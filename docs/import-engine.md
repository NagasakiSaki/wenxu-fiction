# 文档导入与长篇章节识别

## 处理顺序

1. 验证文件类型、大小和 DOCX ZIP 展开规模。
2. TXT / Markdown 自动解码 UTF-8、GB18030、带 BOM 的 UTF-16；DOCX 经 Mammoth 和 Turndown 转成保留段落及加粗标记的文本；PDF 提取可选文字。
3. 标题规范化去掉 Markdown、加粗/斜体和括号装饰，支持“第N章/回/集/幕/话/篇”、Chapter、Episode、EP。不会把“第11集 - 第22集规划”或“第11集完结”当成新章。
4. 先分析整篇的章节结构，再选取边界；明确编号优先，Markdown 同级标题作回退。代码围栏和章内小节不作为章节。
5. 提取书名、副标题和标注的书前资料。`【作品进度】`、原作背景、篇幅体量等保留为 `importNotes`，真正的前言文字仍保留为序言。正文不做摘要或截断。
6. 批量文档按目录和编号自然排序，显示文件来源、章节标题、字符数和原文行号，确认后写入草稿。

Word 中的大字、居中或加粗普通段落不一定是正式 Heading 样式，因此章节识别必须依赖转换后的文字规则，不能只认 HTML / Markdown 标题级别。

## 长篇与保存

正文提取、合并、作品校验统一使用 `src/limits.js` 中的 200 万字符上限；每部仍限 1000 章，单文件 10 MB，每批最多 100 文档 / 50 MB。达到边界时明确报错，保留原草稿。

草稿使用 IndexedDB，兼容并迁移旧的 `wenxu-draft` localStorage 数据。保存使用快照和顺序队列，防止后续编辑污染正在写入的内容；手动保存和导入结果等待事务完成后再显示成功。书架、阅读进度、主题等小数据继续使用 localStorage。本机存储不能替代文件备份。

## 验证与复现

```powershell
npm ci
npm test
node scripts/audit-documents.mjs "本机文档文件夹" ".artifacts/corpus-report.json"
npm run build
```

扫描脚本只读本机文件，不上传内容。报告包含文件名、长度、数量和首末标题，不包含正文；报告仍可能含私人文件名，应留在被 Git 忽略的 `.artifacts/` 中。DOCX 预检使用同一 Mammoth/Turndown 转换方向，浏览器导入额外执行 DOMPurify 清理；发布前还应选择真实 DOCX、TXT 在浏览器确认目录与刷新恢复。

自动化测试使用合成文本，不包含用户作品。覆盖45集在纯文本、Markdown和Word粗体段落下的等价识别，超过旧20万字符的长篇、元数据/正文区分、结束标记、区间标题、UTF-16/GB18030、合并上限，以及百万字中文草稿的写入、迁移和快照顺序。
